# 로또번호 추첨기 · 토스인앱 서비스 기획서

Oct 12, 2026 · @jaeil jeong

## 1. 서비스 개요

토스 안에서 3초 만에 이번 주 로또 번호를 뽑고, 저장하고, 추첨 후 당첨 여부까지 확인하는 미니앱이다. 백엔드 서버 없이 클라이언트와 정적 데이터만으로 운영한다.

**핵심 가치 3가지**

- **빠름:** 진입 후 첫 화면에서 바로 번호를 뽑는다. 가입, 설정, 튜토리얼이 없다.
- **재미:** 드럼 연출, 공 착지 모션, 햅틱으로 "뽑는 맛"을 만든다.
- **기록:** 뽑은 번호를 저장하고, 토요일 추첨 후 자동으로 당첨 결과를 보여준다.

**타깃 사용자**

| 유형 | 상황 | 이 앱에서 원하는 것 |
| --- | --- | --- |
| 정기 구매자 | 매주 로또를 사는데 번호 고르기가 귀찮다 | 빠른 뽑기, 저장, 당첨 확인 |
| 조건파 | 좋아하는 숫자나 피하고 싶은 숫자가 있다 | 고정수·제외수 설정 |
| 재미파 | 사지는 않지만 "이번 주 내 번호"가 궁금하다 | 연출, 공유 |

**하지 않는 것:** 로또 구매 대행, 결제, 당첨 확률을 높여준다는 분석이나 예측. 이 앱의 번호는 무작위 추천이며 당첨 가능성은 직접 고르는 것과 같다.

**성공 기준 (제안, 출시 후 8주):** 뽑기를 한 사용자 중 다음 주에도 다시 뽑는 비율 30% 이상, 저장한 번호의 당첨 확인 진입률 50% 이상.

## 2. 전제와 제약

서버가 없으므로 모든 상태는 기기에 저장하고, 외부 데이터는 정적 파일 하나만 읽는다. 이 전제가 기능 범위를 결정한다.

| 제약 | 영향 | 대응 |
| --- | --- | --- |
| 백엔드 서버 없음 | 계정, 기기 간 동기화, 서버 랭킹, 푸시 스케줄링 불가 | 앱인토스 SDK의 `Storage`(네이티브 저장소)에 로컬 저장. 기기를 바꾸면 기록이 사라진다는 점을 저장 화면에 안내 |
| 당첨번호를 받아올 서버 없음 | 추첨 결과 자동 확인이 어려움 | 정적 JSON 파일을 GitHub Pages 등 정적 호스팅에 두고, 스케줄 작업(GitHub Actions 등)이 매주 갱신 (6장) |
| 앱인토스 웹뷰 환경 | `AsyncStorage` 사용 불가, 내비게이션 바는 토스가 제공 | SDK `Storage`와 Cache API 사용, 상단 바는 그리지 않음 |
| 사행성 정책 | 사행성 서비스는 론칭이 제한될 수 있음 | 구매·결제·당첨 예측 기능을 넣지 않고 "재미로 뽑는 무작위 추천"으로 포지셔닝 (8장) |

정적 JSON 갱신 작업은 엄밀히는 서버가 아니라 "정해진 시간에 파일을 다시 만드는 스크립트"다. 이것도 두고 싶지 않다면 당첨 확인은 v1.1로 미루고 MVP는 뽑기와 저장만 낸다.

## 3. 기능 범위

MVP는 "뽑기 → 저장 → 복사" 한 바퀴만 완성한다. 재방문을 만드는 당첨 확인은 v1.1의 1순위다.

| 순위 | 기능 | 릴리스 | 왜 이 순서인가 |
| --- | --- | --- | --- |
| 1 | 번호 뽑기 (6개, 1\~45 중복 없음, 오름차순) | MVP | 서비스의 존재 이유 |
| 2 | 드럼 연출 + 공 착지 모션 + 햅틱, 건너뛰기 | MVP | 다른 추첨기와의 차별점 |
| 3 | 번호 저장 (회차별, 최대 50개) | MVP | 뽑기를 "내 번호"로 만듦 |
| 4 | 번호 복사 / 공유 | MVP | 판매점·지인에게 전달하는 실사용 동선 |
| 5 | 한 번에 5게임 뽑기 | MVP | 로또 1장 = 5게임이라 수요가 큼, 구현 비용 작음 |
| 6 | 당첨 확인 (저장 번호 vs 추첨 결과, 등수 표시) | v1.1 | 토요일 이후 재방문 동기. 정적 JSON 필요 |
| 7 | 고정수·제외수 조건 뽑기 | v1.1 | 정기 구매자 잔존용 |
| 8 | 주간 기록 (지난 회차 번호와 결과) | v1.1 | 당첨 확인이 쌓이면 자연스럽게 생김 |
| 9 | 오늘의 운세형 테마 번호 (생일, 띠 등 입력 기반) | 이후 | 재미 요소. 근거 없는 "행운" 주장은 피함 |
| 10 | 인앱 광고 (보상형으로 추가 뽑기 연출 등) | 이후 | 지표 확인 후 판단 |

**의도적으로 뺀 것:** 과거 당첨번호 통계·"잘 나오는 번호" 분석. 로또는 매 회 독립 시행이라 통계 추천은 사실과 다르고, 사행성 심사에서도 불리하다.

## 4. 정보 구조와 사용자 흐름

홈이 모든 동선의 중심이고, 뽑기는 홈 → 드럼 → 결과 카드의 한 방향으로만 흐른다. 재방문은 토요일 추첨 후 홈 배너에서 당첨 확인으로 이어지는 고리가 만든다.

&#91;embedded content: 사용자 흐름 · 화면 9개\]

결과 카드에서는 다시 뽑기, 복사·공유, 저장 세 갈래로 나뉜다. 저장한 번호는 추첨 후 당첨 확인의 입력이 된다.

## 5. 화면별 상세 명세

화면은 홈 하나를 중심으로 하고, 나머지는 홈에서 열리는 오버레이나 하위 화면이다. 디자인은 캔버스의 "최종안" 시안을 기준으로 한다.

### 5.1 홈

- **상단:** 회차와 추첨일("\[회차\]회 추첨 · 토 20:35"), 오늘 뽑은 횟수 칩, 제목 "이번 주 행운 번호를 뽑아볼까요?"
- **번호 카드:** 공 6개. 첫 진입 시에는 "오늘의 추천 번호"를 미리 뽑아 보여줘서 빈 화면을 없앤다. 아래에 \[번호 복사\] \[저장하기\].
- **저장한 번호:** 이번 회차에 저장한 번호를 A\~E로 최대 5줄 표시, 더 있으면 "전체 보기".
- **하단 고정 CTA:** \[번호 뽑기\] / 뽑은 후에는 \[다시 뽑기\]. 보조 버튼으로 \[5게임 한 번에\].
- **추첨 후(토 20:35 이후 \~ 다음 회차 전):** 카드 위에 "이번 주 결과가 나왔어요 → 내 번호 확인" 배너 (v1.1).

### 5.2 드럼 연출 오버레이

- 뽑기 버튼을 누르면 전체 화면 오버레이, 드럼 회전 1.4초 후 페이드아웃 → 카드에 공 착지.
- 오른쪽 위 \[건너뛰기\]는 즉시 착지 단계로 넘어간다.
- 번호는 버튼을 누르는 순간 확정한다. 연출 중 이탈해도 결과는 같다.
- 같은 날 3번째 뽑기부터는 연출 0.8초로 단축 (피로도 관리, 설정에서 끄기 가능).

### 5.3 5게임 뽑기

- 5게임을 한 번에 생성해 A\~E 리스트로 보여준다. 공이 줄마다 순서대로 뒤집혀 나타난다.
- &#91;전체 저장\] \[전체 복사\]. 복사 형식: `A 3 11 19 27 34 42` 줄바꿈 구분.

### 5.4 저장 목록

- 회차별 그룹, 최신 회차가 위. 각 줄: 라벨, 공 6개, 뽑은 시각, 삭제(스와이프 또는 더보기).
- 상단 안내 한 줄: "번호는 이 기기에만 저장돼요".
- 결과가 나온 회차는 줄마다 등수 뱃지(1\~5등 / 낙첨)와 맞은 번호 강조 (v1.1).

### 5.5 조건 설정 (v1.1)

- 1\~45 번호판, \[고정수\] \[제외수\] 탭. 고정수 최대 5개, 제외수 최대 30개.
- 한도를 넘기면 해당 칸 흔들림 + 안내 문구.
- 조건은 기기에 저장되어 다음 뽑기에도 유지, 홈 카드에 "조건 적용 중" 칩 표시.

### 5.6 당첨 확인 (v1.1)

- 회차의 당첨번호 6개 + 보너스 1개를 상단에 표시.
- 저장한 번호마다 맞은 개수와 등수를 계산해 표시. 계산은 클라이언트에서 한다.
- 등수 기준: 6개 일치 1등, 5개 + 보너스 2등, 5개 3등, 4개 4등, 3개 5등.
- 당첨금은 표시하지 않거나, 정적 JSON에 있을 때만 "참고용"으로 표시. 실제 확인은 공식 판매처 안내로 연결.

### 5.7 빈 상태와 오류

| 상황 | 문구 |
| --- | --- |
| 저장한 번호 없음 | 아직 저장한 번호가 없어요 |
| 저장 50개 초과 | 저장은 50개까지 할 수 있어요. 오래된 번호를 지워주세요 |
| 당첨번호 불러오기 실패 | 결과를 아직 불러오지 못했어요. 잠시 후 다시 확인해 주세요 |
| 추첨 전 결과 진입 | 토요일 20:35 추첨 후에 확인할 수 있어요 |

## 6. 서버리스 데이터 설계

사용자 데이터는 전부 SDK `Storage`에 JSON으로 저장하고, 당첨번호만 정적 JSON 파일에서 읽는다. 쓰는 곳은 기기 하나뿐이라 동기화 문제가 없다.

### 6.1 저장 키

| 키 | 내용 | 크기 상한 |
| --- | --- | --- |
| `lotto:v1:saved` | 저장한 번호 목록 | 50개 |
| `lotto:v1:prefs` | 고정수, 제외수, 연출 끄기 여부 | 1개 |
| `lotto:v1:daily` | 오늘 날짜와 뽑은 횟수 (연출 단축 판단용) | 1개 |
| `lotto:v1:results` | 받아온 당첨번호 캐시 (최근 10회차) | 10회차 |

키에 `v1`을 넣어 두면 구조를 바꿀 때 마이그레이션을 키 단위로 할 수 있다.

### 6.2 데이터 모델

```json
{
  "saved": [
    { "id": "uuid", "round": 1195, "numbers": [3, 11, 19, 27, 34, 42], "createdAt": "2026-10-12T09:30:00+09:00", "source": "single" }
  ],
  "prefs": { "fixed": [7, 23], "excluded": [4, 13], "reduceDrum": false }
}
```

`round` 값은 예시다. `source`는 `single` | `five` | `condition` 중 하나로, 어떤 뽑기에서 나온 번호인지 기록해 지표로 쓴다.

### 6.3 회차 계산

회차는 서버 없이 날짜로 계산한다. 기준 회차(첫 추첨일)에서 매주 토요일 추첨 시각마다 1씩 증가한다. 출시 전 실제 최근 회차와 계산 결과를 대조하고, 어긋나면 정적 JSON의 `latestRound`를 우선한다.

### 6.4 당첨번호 (v1.1)

- 정적 파일 예: `results.json` = `{ "latestRound": n, "draws": [{ "round", "date", "numbers": [6개], "bonus" }] }`
- 매주 토요일 추첨 후 스케줄 작업이 파일을 갱신하고, 미니앱은 홈 진입 시 한 번 읽어 `lotto:v1:results`에 캐시한다.
- 캐시된 최신 회차가 이미 있으면 다시 요청하지 않는다. 추첨 직후에는 갱신 지연이 있을 수 있어 "결과 준비 중" 상태를 둔다.
- 데이터 출처와 수집 방식의 이용약관은 11장 오픈 이슈로 남긴다.

### 6.5 번호 생성

- `crypto.getRandomValues`로 1\~45 중 6개를 중복 없이 뽑고 오름차순 정렬한다.
- 조건 뽑기: 고정수를 먼저 넣고, (전체 − 고정수 − 제외수) 풀에서 나머지를 채운다. 풀이 부족하면 버튼을 비활성화한다.

## 7. 인터랙션 · 모션 · 햅틱

뽑기 한 번은 약 2.8초짜리 연출이고, 햅틱은 그 안의 세 시점에만 넣는다. 수치는 캔버스 최종안 기준이며 실기기에서 조정한다.

| 시점 (기본 연출) | 화면 | 모션 | 햅틱 |
| --- | --- | --- | --- |
| 0ms | 버튼 탭 | 버튼 눌림 (scale 0.965) | 약한 탭 |
| 0–1400ms | 드럼 오버레이 | 페이드인 220ms, 드럼 스프링 등장, 공 회전, 진행 바 | 없음 |
| 1400–1660ms | 오버레이 퇴장 | 드럼 확대되며 페이드아웃 | 없음 |
| 1780ms\~, 130ms 간격 6회 | 카드 | 공이 위에서 떨어져 스프링 착지 (550ms) | 공마다 짧은 틱 |
| 약 2750ms | 카드 | 테두리 링 확산 + 컨페티 | 성공 1회 |

**규칙**

- 햅틱은 앱인토스 SDK의 햅틱 API로 호출한다. 지원 타입은 개발 착수 시 SDK 문서에서 확인해 위 표의 세 종류에 매핑한다.
- 기기의 "동작 줄이기"가 켜져 있으면 드럼 연출을 생략하고 공은 페이드로만 나타난다. 햅틱은 유지한다.
- 연출 중에는 뽑기·저장·복사 버튼을 비활성화해 이중 입력을 막는다.
- 이탈 후 복귀하면 연출을 다시 재생하지 않고 결과 상태로 바로 보여준다.

## 8. 정책 · 심사 · 법적 리스크

가장 큰 리스크는 기능이 아니라 심사다. 앱인토스는 사행성 서비스의 론칭을 제한할 수 있다고 밝히고 있고, 2026년 8월부터 개별 표현뿐 아니라 서비스 전체 맥락까지 보도록 검수 기준을 강화했다. 개발 전에 이 앱이 어느 쪽으로 읽히는지 먼저 확인해야 한다.

| 리스크 | 대응 |
| --- | --- |
| "로또" 주제 자체가 사행성으로 판단될 가능성 | 개발 착수 전 앱인토스 콘솔 문의나 서비스 오픈 정책 문서로 확인. 안 되면 "행운 번호 뽑기" 같은 범용 랜덤 추첨기로 포지셔닝 변경 |
| 당첨 가능성을 높여준다는 오해 | "이 번호는 무작위로 뽑은 추천이며 당첨 확률은 같아요" 고지를 홈 하단과 앱 설명에 표시 |
| 구매 유도로 읽히는 문구 | "지금 사세요", 판매점 연결, 당첨금 강조 문구를 쓰지 않음 |
| 공식 로또 상표·로고 사용 | 동행복권 로고, 공식 용지 디자인을 쓰지 않음. 공 색 구분은 일반적인 번호대 색상으로만 사용 |
| 당첨번호 데이터 수집 | 공식 사이트의 이용약관과 수집 허용 여부 확인. 확인 전에는 당첨 확인 기능을 출시하지 않음 |
| 미성년자 이용 | 복권은 만 19세 미만 구매 불가. 앱 설명에 "재미로 즐기는 번호 추천"임을 명시하고 구매 기능은 두지 않음 |

## 9. 지표와 성장 장치

북극성 지표는 "주간 재방문 사용자 비율"이다. 로또는 주 단위로 소비되므로, 이번 주에 뽑은 사람이 다음 주에 다시 오는지가 서비스의 전부다.

| 지표 | 정의 | 목표 (제안) |
| --- | --- | --- |
| 주간 재방문율 | W주 뽑기 사용자 중 W+1주에도 뽑은 비율 | 30% |
| 저장률 | 뽑기 세션 중 1개 이상 저장한 비율 | 40% |
| 당첨 확인 진입률 (v1.1) | 번호를 저장한 사용자 중 결과 화면을 연 비율 | 50% |
| 연출 건너뛰기율 | 드럼 연출 중 건너뛰기를 누른 비율 | 30% 이하 유지, 넘으면 연출 단축 |

서버가 없으므로 지표는 앱인토스 콘솔이 제공하는 데이터 대시보드와 SDK의 이벤트 로깅 지원 범위 안에서 본다. 착수 전에 어떤 커스텀 이벤트를 남길 수 있는지 확인한다.

**성장 장치 (우선순위 순)**

1. **토요일 결과 배너:** 추첨 후 홈에 "내 번호 확인" 배너. 재방문의 핵심 트리거.
2. **공유:** 뽑은 번호를 이미지 카드로 공유 ("내 이번 주 번호"). 토스 공유 기능 사용.
3. **검색 키워드:** 앱 정보에 "로또 번호", "번호 추첨", "행운 번호" 등록.
4. **광고 수익화:** 앱인토스는 2026년 8월 28일부터 사업자 등록 없이 인앱 광고를 시작할 수 있다. 연출을 해치지 않는 위치(저장 목록 하단 등)에서만 검토한다.

## 11. 오픈 이슈

착수 전에 1번을 먼저 닫아야 한다. 나머지는 MVP 개발과 병행해도 된다.

- [ ] 로또 번호 추천이 앱인토스 서비스 오픈 정책상 출시 가능한 카테고리인지 확인 (콘솔 문의 또는 정책 문서)
- [ ] 당첨번호 데이터 출처의 이용약관과 수집 허용 여부
- [ ] 정적 JSON 갱신 작업(GitHub Actions 등)을 둘지, 당첨 확인을 미룰지 결정
- [ ] SDK에서 쓸 수 있는 햅틱 타입과 커스텀 이벤트 로깅 범위 확인
- [ ] 앱 이름: "로또"를 이름에 넣을지, "행운 번호" 계열로 갈지 (정책 확인 결과에 따라)
- [ ] 인앱 광고를 넣을지, 넣는다면 위치
